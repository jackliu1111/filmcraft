## 恢复与异常关联

工程继续内嵌保存识别事件、分析容器音轨与 native ordinal 映射、各候选的人工范围、独立手动补片、剪辑顺序、每条保留音轨和静音、组稿文件关系，以及队列状态。组稿原稿和编辑副本角色仍由已有 `selection.assembly` 与文件保护判断。队列重开后维持 #28 的 interrupted／主动重试语义；不会自动提交分析或建片段。

新增公开 `recognition.recovery {item}`，给出 `status`、`reason`、`code`、`resultId`、`audioStream`、`path`、`projectToken`。状态区分未分析、关联待核对、有效、关联缺失／不可用和源离线。只有持有 result provenance 的范围、组稿或完成队列却丢失识别关联时才报缺失；纯手工划选仍是“未分析”。现场路径／大小／修改时间和音轨映射的轻量检查不能代替共享核心的完整内容核验。

桌面在重开后用同一个桥接 worker 串行核对已存关联，与实际分析互斥。`apexAi.inspect` 增加 `associations`、`activeValidation`；核对期间 busy 为 true，但 activeJob／activeAttempt 为 null，可与分析任务区分。校验缺失、损坏、模型配置变化或目录被占用均显示原因，保留原有事件／范围／片段。异常写入独立的 `recognition.association` 元数据，不占编辑撤销步；保存重开仍可看到原因。有效关联的只读核对只更新会话证明，不使干净工程变脏；修复既有警告时才持久更新其状态。工程 incarnation、当前 result ID 以及成功回报的源身份／音轨均须匹配，迟到核对不能修改另一工程。

“核对已存分析”只读检查，“重新分析此原片”才主动进入 #28 的重试路径。恢复外部文件后可以只核对，不必重推理。切换工程清除旧路径、试听证明、进度与错误，重新加载当前工程来源和组稿关系。尚未分析的枪声、人声子行统一显示未分析，不把它显示成缺少人声分数。

## 公共桥接入口

```sh
MODEL_PYTHON integrations/apex-ai/bridge.py validate \
  --input /ABSOLUTE/source.mkv --audio-stream CONTAINER_INDEX \
  --result-id COMPLETED_PREDICTION_ID
```

沿用 APEX_SERVICE_ROOT／APEX_MODEL_WORKSPACE／APEX_AI_DATA_DIR 等环境。正常服务锁与中断清理仍由共享服务管理。“只读”指不会调用 analyze、confirm_audio、probe_media、recompute_candidates 或改写既有预测／候选；服务初始化仍沿用自身恢复清理。检查失败没有分析 fallback。

FilmCraft 适配层先限定精确预测 ID 和关联文件位置，拒绝符号链接或外部 scores_path，核对完成任务中该预测与 media 的关联；批任务 ID 可以与 prediction ID 不同。检查 prediction.json、NPZ 必需数组和 ZIP 完整性后，复用共享 `validate_result` 及现有分页 `read_scores` 消费路径，检查当前源完整内容、所选分析音轨、模型／配置与分数内容。`get_result` 只读取 JSON，单独成功并不构成缓存有效证明。成功仅输出 `type=validation,status=valid`，失败输出结构化 error，不发布替换事件。

实际分析的命中和失效仍由共享后端缓存准入处理，不另建缓存。其身份包含全文件 SHA256、大小与纳秒 mtime、源路径、所选音轨及时间映射，以及权重／模型适配器／加载脚本和配置版本。这里不宣称覆盖所有运行库的身份。

桌面命令与自动化 ID：

- `apexAi.open {item}` 后 `apexAi.validate {item}`；按钮 ID `apexAi.validate`。
- `apexAi.cancelValidation {}`；只取消关联核对，不改已存事件。
- `apexAi.retry {item}`；“重新分析此原片”按钮 ID `apexAi.retryAssociation`，多轨仍需按 #27 试听后确认。
- `recognition.validated {item,resultId,projectToken,validation|error,code?}` 为公开结果接收边界，成功必须提供完整桥接 validation 身份。
